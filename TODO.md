Pre-existing issues found during implementation of `map-painter-visible-object-cull`, not initiated by that change. Process in separate changes.

- **The label layouter's viewport belongs to the previous frame in the early render steps**: a backend reports the viewport of a frame from its drawing target in `BeforeDrawingCallback` (the `Prerender` step 7, for example `MapPainterCairo.cpp:700`), while the way shield labels are registered in step 3, in front of it. A label decision taken in the early steps therefore sees the viewport of the previous frame (or an empty one in the first frame). The change handles this by only deciding a label when the viewport of the frame has been reported (`SetViewport` marks it, `Reset` clears the mark), so the shield labels of a frame are not decided by the shared label stage; their rejection happens in the painter, which uses the projection. A cleaner arrangement would report the viewport at the start of a frame (the painter's `InitializeRender`) from the drawing target, but the viewport of a tiled backend is the rectangle of the target within the surface and only the backend knows it.
- **`LabelLayouter::RegisterLabel(const LabelData&)` cannot be instantiated**: the single element overload sets `instance.ref` and `instance.basemap`, which a `LabelInstance` does not have (it carries the object reference and the basemap flag in its `LabelPriority`). The overload is not called by any backend today, so the error stays latent; the change fixes it to set the priority, as the element list overload does. Whoever adds a caller of that overload would otherwise hit a compile error.
- **A per-object label element store in the point label path**: `MapPainter::LayoutPointLabels` builds a `std::vector<LabelData>` (plus the label texts) for every loaded point object or area whose type has label styles, before the early decision can be taken, because the extent of a label is set by its text. The vector is a per-object allocation that a reused painter member would remove (the same shape as the reused `textStyles` and `borderStyles` stores); it is not part of this change, which would collide with the scratch storage the unmerged `map-painter-label-reuse` branch rewrites.
- **Way line style resolution has no observation hook for tests**: `MapParameter::RegisterFillStyleProcessor` makes the per-ring fill style resolution of the area path observable, but there is no counterpart for the line styles of a way. The unit tests of the way rejection can therefore only guard the contract (a way outside the view adds no prepared way, no coordinates and no shield label) and its regression properties; that the early rejection *removes work* is verified by the before/after measurement of the step (`map-painter-visible-object-cull`, `verification.md`) instead. A line style processor would close that gap.

Pre-existing issues found during import-performance analysis of the `further-types-styles-symbols-and-fixes` branch (671 -> 1527 types). Process in separate changes.

- **Type resolution is a linear scan over all types**: `TypeConfig::GetNodeType`/`GetWayAreaType`/`GetRelationType` (`libosmscout/src/osmscout/TypeConfig.cpp:1026-1096`) iterate all types and evaluate tag conditions per object during import. Measured: +47% Preprocess time with 1527 vs 671 types (16 threads, PBF). Early matches (e.g. `highway=residential`) show no slowdown; late-match and no-match objects pay the full scan. Ways are the biggest victim (`GetWayAreaType` scans way+area types, 536 -> 1289). Fix: build a tag-key dispatch index in `TypeConfig` (39 primary tag keys discriminate all 1489 types; 1078/1489 are simple `"key"=="value"` conditions). Index conditions by referenced TagId, evaluate only types whose keys are present in the object's tag map. Preserve match order (first match in `types` order wins). Handle NOT-containing conditions via a fallback list (0 pure-NOT conditions exist today, but keep the fallback for robustness).
- **PBF reader drops unregistered tags**: `PreprocessPBF.cpp:312` (`if (id!=tagIgnore)`) discards tags not registered in the type definition. This means no-match objects in real imports are those with registered keys but non-matching values (e.g. `highway=foobar`), not arbitrary unknown tags. Affects how no-match cost should be estimated; also means `source`/`note`-only objects take the empty-tag fast path.
- **Micro-benchmark underestimates import type-resolution cost ~2-3x**: `Tests/src/TypeResolutionPerformanceTest.cpp` (new) measures per-call cost with hot cache; import measurements (cold cache, tagMap construction, string compares on hits) are ~2-3x higher per call. Use import-level measurements as ground truth.
- **Type ID byte width**: 854 node types / 1097 area types -> 2-byte type IDs in `node.dat`/`area.dat`/raw files (was 1 byte under 256 types). Minor size/read cost, not a bottleneck.
- **Ways-specific resolution cost**: `GetWayAreaType` scans all way+area-capable types (536 -> 1289) and evaluates conditions for both way and area resolution in one pass. Measured per-call (hot cache): no-match 3.58us -> 8.64us, building=yes 2.78us -> 7.07us; early matches (highway=*) unaffected (match position unchanged). Import-level: 500k ways 2.12s -> 4.41s (16 threads). The way/area condition set is dominated by a few keys: shop 377, amenity 147, office 100, historic 86, landuse 49, leisure 47. The tag-key index fixes this: a highway=residential way evaluates 19 highway-keyed conditions instead of 1289. Primary-key extraction rules: AND -> first child's key; OR -> each branch's first key (33 multi-key OR conditions exist, e.g. `"waterway"=="riverbank" OR ("natural"=="water" AND ...)`); NOT -> inner key + fallback list; leaf -> its key. Only 3 types have "building" as primary key (generic building type is `EXISTS "building" AND !(...)`); the ~680 building-referencing conditions are secondary (keyed on landuse/leisure/amenity etc.). Preserve match order by collecting candidates from the object's tags and sorting by type index before evaluation. Secondary optimization: geometry-aware split (open ways skip area resolution, closed ways skip way resolution unless pinWay) — the WaySubTask knows geometry before resolution.
- **Value-level type index (follow-up to the tag-key dispatch index)**: with the tag-key index, a no-match object on a crowded key (e.g. `amenity=foobar`, 147 conditions) still evaluates every condition of that key. A value-level reverse index (condition matches -> key+value pair) would make no-match objects O(1) per key. Deferred: the key-level index already eliminates the type-count growth penalty (import Preprocess flat at 671 vs 1527 types).

Pre-existing issues found during implementation of `map-painter-area-visibility-cull`, not initiated by that change. Process in separate changes.

- **Area preparation early-out that no shipped style sheet reaches**: `MapPainter::PrepareAreaRing` returns early when a ring resolves neither a fill nor a border style (`libosmscout-map/src/osmscoutmap/MapPainter.cpp`, the `if (!fillStyle && borderStyles.empty())` test). Measured on the Dortmund database at zoom 15 with `stylesheets/standard.oss`, every ring of every loaded area resolves at least one style, so `styled == rings == 17650` and the early-out is never taken. The check is therefore not dead code in general (a custom style sheet can reach it) but it does not reduce the work of the area preparation step with the shipped style sheets. Not part of `map-painter-area-visibility-cull`, which does not touch it.
- **Millimetre border width used as a pixel offset in the per-ring visibility decision**: `MapPainter::PrepareAreaRing` passes `borderStyle->GetWidth()/2.0` as the `pixelOffset` of `MapPainter::IsVisibleArea`, while `GetWidth()` returns millimetres, an offset in pixels is expected, and the backends convert the same value with `Projection::ConvertWidthToPixel` (for example `MapPainterCairo::DrawFillStyle`). At 96 DPI the effective tolerance is therefore about 3.8x smaller than the stated width suggests. The derived bound of `map-painter-area-visibility-cull` deliberately uses the same non-converted expression so that it cannot be smaller than any per-ring tolerance, and a debug assert in that path enforces the relationship; converting the per-ring tolerance to pixels would require converting that bound in the same change. Behaviour change, so not part of that change.
- **OpenGL backend reprocesses all loaded areas per data load**: `MapPainterOpenGL::ProcessAreas` (`libosmscout-map-opengl/src/osmscoutmapopengl/MapPainterOpenGL.cpp`) walks every loaded area of every tile and, per ring, copies the ring nodes into a temporary vector, removes duplicate points with a nested loop over all point pairs *before* testing visibility, copies inner rings into another vector and triangulates every visible ring on the CPU; it also copies and sorts the whole loaded area list per call. Measured on the zoom 15 fixed view (17629 loaded areas, 726 visible rings): 87 ms and 156 621 allocations per `ProcessData` call, against 5 ms and 158 allocations for the equivalent core painter step. Caveats for whoever picks this up: the duplicate point removal is quadratic per ring and runs before the visibility test, so most of that work serves rings that are then discarded; in `OSMScoutOpenGL` `ProcessData` runs on a worker thread inside an asynchronous data load, so this is pan latency rather than frame cost, while `Tests/src/PerformanceTest.cpp` drives it once per frame and therefore reports it as a frame cost; and the OpenGL performance tests need both `--shaders libosmscout-map-opengl/data/shaders` and a `--font` that exists on the machine (see the shader entry above) before they can be run at all.
- **LeakSanitizer reports from fontconfig/pango fail three text-rendering tests in the sanitizer build**: in the `build-asan` configuration documented in AGENTS.md, `ctest --exclude-regex "PerformanceTest"` reports 96 % passed with `MapPainterShieldTest`, `TextMetricsCairoTest` and `TextMetricsSVGTest` failing (`LeakSanitizer: detected memory leaks`, for example 65536 bytes in 256 objects). The assertions of all three tests pass; every allocation frame of the report is inside `libfontconfig.so.1` (`FcFontSetList`) or `libpango-1.0.so.0`, reached from the unmodified `MapPainterCairo::Layout`, and no frame is in libosmscout code. With `ASAN_OPTIONS=detect_leaks=0` all three pass. This is the same class of failure that currently excludes `PerformanceTest` from the sanitizer job ("UI libraries leak on exit"). Options: add a LeakSanitizer suppression file for fontconfig/pango, exclude these tests the way `PerformanceTest` is excluded, or set `detect_leaks=0` for them. Not investigated further during `map-painter-area-visibility-cull`, which does not touch text rendering; no pre-change sanitizer build was produced, so their pre-existence rests on the report contents above.

Pre-existing issues found during implementation of `navigation-gps-jitter`, not initiated by that change. Process in separate changes.

- **The position-difference speed fallback never runs at fix rates above 1 Hz**: `SpeedAgent::Process` (`libosmscout/src/osmscout/navigation/SpeedAgent.cpp`) computes the fallback speed only when `gpsUpdateMsg->timestamp-lastPosition.time >= seconds(1)`, but `lastPosition` is updated on *every* accepted fix, so that difference is always the interval between two consecutive fixes. With a 4 Hz receiver that reports no speed of its own the segment is 0.25 s and the condition is never met: the agent publishes no `CurrentSpeedMessage` at all - for a moving vehicle as well as for a standing one. Measured with `Tests/src/SpeedAgentTest.cpp` driven at 4 Hz: every published speed is absent, while the same walk at 1 Hz reports 4 km/h. The guard presumably means "do not derive a speed from a segment shorter than a second", which needs a separate accumulator (or a comparison against the oldest fix of the window) instead of a comparison against `lastPosition`. Not part of `navigation-gps-jitter`, which only decides whether the fixes of a >= 1 s segment describe a standing vehicle.
