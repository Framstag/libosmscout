Pre-existing issues found during implementation of `map-painter-visible-object-cull`, not initiated by that change. Process in separate changes.

- **The label layouter's viewport belongs to the previous frame in the early render steps**: a backend reports the viewport of a frame from its drawing target in `BeforeDrawingCallback` (the `Prerender` step 7, for example `MapPainterCairo.cpp:700`), while the way shield labels are registered in step 3, in front of it. A label decision taken in the early steps therefore sees the viewport of the previous frame (or an empty one in the first frame). The change handles this by only deciding a label when the viewport of the frame has been reported (`SetViewport` marks it, `Reset` clears the mark), so the shield labels of a frame are not decided by the shared label stage; their rejection happens in the painter, which uses the projection. A cleaner arrangement would report the viewport at the start of a frame (the painter's `InitializeRender`) from the drawing target, but the viewport of a tiled backend is the rectangle of the target within the surface and only the backend knows it.
- **`LabelLayouter::RegisterLabel(const LabelData&)` cannot be instantiated**: the single element overload sets `instance.ref` and `instance.basemap`, which a `LabelInstance` does not have (it carries the object reference and the basemap flag in its `LabelPriority`). The overload is not called by any backend today, so the error stays latent; the change fixes it to set the priority, as the element list overload does. Whoever adds a caller of that overload would otherwise hit a compile error.
- **A per-object label element store in the point label path**: `MapPainter::LayoutPointLabels` builds a `std::vector<LabelData>` (plus the label texts) for every loaded point object or area whose type has label styles, before the early decision can be taken, because the extent of a label is set by its text. The vector is a per-object allocation that a reused painter member would remove (the same shape as the reused `textStyles` and `borderStyles` stores); it is not part of this change, which would collide with the scratch storage the unmerged `map-painter-label-reuse` branch rewrites.
- **Way line style resolution has no observation hook for tests**: `MapParameter::RegisterFillStyleProcessor` makes the per-ring fill style resolution of the area path observable, but there is no counterpart for the line styles of a way. The unit tests of the way rejection can therefore only guard the contract (a way outside the view adds no prepared way, no coordinates and no shield label) and its regression properties; that the early rejection *removes work* is verified by the before/after measurement of the step (`map-painter-visible-object-cull`, `verification.md`) instead. A line style processor would close that gap.

Issues found during analysis of the `further-types-styles-symbols-and-fixes` branch (PR #1782, 671 -> 1527 types), covering import speed, database size, data loading speed and rendering speed. Process in separate changes.
- **Type resolution is a linear scan over all types**: `TypeConfig::GetNodeType`/`GetWayAreaType`/`GetRelationType` (`libosmscout/src/osmscout/TypeConfig.cpp:1026-1096`) iterate all types and evaluate tag conditions per object during import. Measured: +47% Preprocess time with 1527 vs 671 types (16 threads, PBF). Early matches (e.g. `highway=residential`) show no slowdown; late-match and no-match objects pay the full scan. Ways are the biggest victim (`GetWayAreaType` scans way+area types, 536 -> 1289). Fix: build a tag-key dispatch index in `TypeConfig` (39 primary tag keys discriminate all 1489 types; 1078/1489 are simple `"key"=="value"` conditions). Index conditions by referenced TagId, evaluate only types whose keys are present in the object's tag map. Preserve match order (first match in `types` order wins). Handle NOT-containing conditions via a fallback list (0 pure-NOT conditions exist today, but keep the fallback for robustness).
- **PBF reader drops unregistered tags**: `PreprocessPBF.cpp:312` (`if (id!=tagIgnore)`) discards tags not registered in the type definition. This means no-match objects in real imports are those with registered keys but non-matching values (e.g. `highway=foobar`), not arbitrary unknown tags. Affects how no-match cost should be estimated; also means `source`/`note`-only objects take the empty-tag fast path.
- **Micro-benchmark underestimates import type-resolution cost ~2-3x**: `Tests/src/TypeResolutionPerformanceTest.cpp` (new) measures per-call cost with hot cache; import measurements (cold cache, tagMap construction, string compares on hits) are ~2-3x higher per call. Use import-level measurements as ground truth.
- **Type ID byte width is unchanged by this branch**: measured by running `Tests/src/TypeResolutionPerformanceTest.cpp` against both type definition files (with the #1787 code), both report `Type ID bytes: node 2, way 1, area 2`. The master type set already has 335 node types and 444 area types and therefore already exceeds the 1-byte range (node ids up to 334, area ids up to 443), so the growth 671 -> 1527 types (854 node, 192 way, 1097 area) causes no size or read cost change in `nodes.dat`/`ways.dat`/`areas.dat` or the raw files.
- **Ways-specific resolution cost**: `GetWayAreaType` scans all way+area-capable types (536 -> 1289) and evaluates conditions for both way and area resolution in one pass. Measured per-call (hot cache): no-match 3.58us -> 8.64us, building=yes 2.78us -> 7.07us; early matches (highway=*) unaffected (match position unchanged). Import-level: 500k ways 2.12s -> 4.41s (16 threads). The way/area condition set is dominated by a few keys: shop 377, amenity 147, office 100, historic 86, landuse 49, leisure 47. The tag-key index fixes this: a highway=residential way evaluates 19 highway-keyed conditions instead of 1289. Primary-key extraction rules: AND -> first child's key; OR -> each branch's first key (33 multi-key OR conditions exist, e.g. `"waterway"=="riverbank" OR ("natural"=="water" AND ...)`); NOT -> inner key + fallback list; leaf -> its key. Only 3 types have "building" as primary key (generic building type is `EXISTS "building" AND !(...)`); the ~680 building-referencing conditions are secondary (keyed on landuse/leisure/amenity etc.). Preserve match order by collecting candidates from the object's tags and sorting by type index before evaluation. Secondary optimization: geometry-aware split (open ways skip area resolution, closed ways skip way resolution unless pinWay) — the WaySubTask knows geometry before resolution.

The key-level index reduces but does not eliminate the type-count growth penalty: measured with the #1787 code, no-match `GetNodeType` grows 1.734 -> 2.696 us and no-match `GetWayAreaType` grows 3.635 -> 9.550 us from 671 to 1527 types (1.55x / 2.63x), because the number of conditions per key grows with the type set (shop 377, building 683 references). This step is 10.7 s of Dortmund's 28.5 s (37.6%) and is the first thing to attack for import wall time in general; the object growth of this branch feeds straight into it.
- **`AreaIndexGenerator::MakeAreaIndex` reads the whole object file once per magnification level, twice**: `libosmscout-import/include/osmscoutimport/AreaIndexGenerator.h:536-569` (`CalculateDistribution`) does `scanner.GotoBegin()` and parses every object once per level, and the write phase repeats that (`:416-458`, `scanner.GotoBegin()` inside the `for (l=areaIndexMinMag; l <= maxLevel; l++)` loop). Pre-existing issues found during implementation of `map-painter-area-visibility-cull`, not initiated by that change. Process in separate changes.

- **Area preparation early-out that no shipped style sheet reaches**: `MapPainter::PrepareAreaRing` returns early when a ring resolves neither a fill nor a border style (`libosmscout-map/src/osmscoutmap/MapPainter.cpp`, the `if (!fillStyle && borderStyles.empty())` test). Measured on the Dortmund database at zoom 15 with `stylesheets/standard.oss`, every ring of every loaded area resolves at least one style, so `styled == rings == 17650` and the early-out is never taken. The check is therefore not dead code in general (a custom style sheet can reach it) but it does not reduce the work of the area preparation step with the shipped style sheets. Not part of `map-painter-area-visibility-cull`, which does not touch it.
- **OpenGL backend reprocesses all loaded areas per data load**: `MapPainterOpenGL::ProcessAreas` (`libosmscout-map-opengl/src/osmscoutmapopengl/MapPainterOpenGL.cpp`) walks every loaded area of every tile and, per ring, copies the ring nodes into a temporary vector, removes duplicate points with a nested loop over all point pairs *before* testing visibility, copies inner rings into another vector and triangulates every visible ring on the CPU; it also copies and sorts the whole loaded area list per call. Its own visibility call passes `borderWidth/2.0` - a width in millimetres - as the `pixelOffset` of `IsVisibleArea`, the defect fixed for the core painter in `openspec/changes/2026-09-20-fix-area-cull-pixel-tolerance`. Deferred findings of `publish-container-images`. Process in separate changes.

- **The reported library version carries no commit identity on unreleased builds**: `OSMSCOUT_IMPORT_VERSION` is the library version alone (`Import/CMakeLists.txt:13` from `OSMSCOUT_LIBRARY_VERSION`; `Import/meson.build:6` from `libraryVersion`), so between two milestones a build of the main branch and the last release both report the same version and a generated `db.json` cannot be traced back to the commit that produced it. The version bump pull request makes released artifacts distinguishable from each other (a release asserts that its revision declares the version it publishes), but a database written between releases still cannot be matched to a commit. A `git describe` suffix in the version, or the source revision recorded in the database metadata, would close it; both change what generated metadata records. The query added by the publishing change (`Import --tool-version`) is the only way to read the version out of an image today.
- **A version tag does not identify released source in the rolling scheme**: the images are tagged with the release version the source declares, and every later build of the same version overwrites that tag, so only the build stamp identifies released content. A `db.json` in hand cannot be traced back to the exact image that wrote it (only to the milestone). Accepting the scheme was a deliberate decision (design decision 2); an immutable per-release tag - which needs a publication path that does not depend on the release event, see the change's design - would close it.
- **Only `linux/amd64` images are published**: `ghcr.io/framstag/libosmscout/mapgen` and `.../mapserve` are amd64 only - a deliberate scope decision (Non-Goals in the change's design), so an arm64 host still has to build locally. Adding `linux/arm64` means either emulating the build stage (the image compiles the core library and the import library) or a native arm64 runner.
- **A pinned build expires after the retention window**: the pruning job keeps the newest 20 publications per image and deletes older ones, so a build stamp stops being pullable once that many newer builds exist. A deployment that pins a stamp has to move to a newer one eventually; a longer window is a one-value change (`KEEP_BUILDS` in `.github/workflows/mapgen_image.yml`, repeated in `Documentation/MapRepository.md`).
- **The version bump is a human step that nothing enforces but the release assertion**: the release workflow cannot write to the main branch (branch protection requires a pull request and `GITHUB_TOKEN` is not an admin), so a forgotten bump is caught only when the release is attempted, and until a milestone sets `version:` in `meson.build` the images carry `latest` and the build stamp only. Closing it would need a bypass entry for the Actions app or a PAT secret in the release workflow.
- **The image build context no longer contains the repository history**: `.dockerignore` excludes `.git/`, which cut the local build context from 107.97 MB to 58.17 MB, but a future build step that reads repository metadata (a version stamp from `git describe`, for example) would now silently see no repository. If such a step is added, drop the `.git/` entry or pass the value in as a build argument instead.
- **The base images are behind the current releases**: `scripts/mapgen/Dockerfile` builds and runs on `ubuntu:noble` (24.04) and `scripts/mapgen/Dockerfile.serve` serves on `nginx:1.27-alpine`, while Docker Hub carries `ubuntu:26.04` and `nginx:1.31-alpine`. Bumping the distro is not a one-line change: the runtime stage installs from a fixed package list (`libprotobuf32`, `libmarisa0`, `libtbb12`, `libxml2`, `liblzma5`, `libzstd1`, `libgomp1`), which a newer release may rename, and the build stage compiles the import tool against the same distro, so it needs a full image build plus the smoke checks to verify. Not done while the publishing change was prepared: no Docker daemon was reachable on the machine that prepared it. The nginx bump is low risk but equally unverified and belongs in the same change.
- **`actions/delete-package-versions@v5` still declares a Node 20 runtime**: it is the current release of that action (checked against `repos/actions/delete-package-versions/releases/latest`), so its two steps keep the runner's `Node 20 is being deprecated` notice even after the other actions in the image workflow were updated to their Node 24 majors. Replacing the two steps with a `gh api` deletion (the API paths are `/users/{owner}/packages/container/{package}/versions`, with the package name URL-encoded) would remove the notice and put the pagination, the retention count and the error handling in our hands.
- **The compose smoke job pays for a second full image build**: `docker compose -f scripts/mapgen/docker-compose.yml build` does not share the `type=gha` build cache that the `verify` and `publish` jobs use, so that job recompiles the core library and the import library on every run. A `cache_from`/`cache_to` pair on the `mapgen` service would remove most of it; the compose file is otherwise unchanged by `publish-container-images`.

Observations of `mapgen-runtime-identity`.

- **A configured identity has no entry in the image's `/etc/passwd`**: the image's own user is `mapgen` (uid 1000, gid 1000), while `PUID`/`PGID` can name any identity, and a pass then runs without user information: `HOME` is pointed at the writable work area for that reason, and the CI smoke run performs a pass as uid/gid `1234` to show that the pass copes. If a tool turns out to need a passwd entry (locale or user lookups are the usual suspects), the options are to document that the identity has to exist in the image or to add a fallback that maps an unknown uid to the `mapgen` entry. The smoke run is what decides this, so the entry stays until it has passed on a runner.

Conditions of `mapgen-cron-schedule`.

- **The scheduler binary is fetched from GitHub releases at image build time**: `scripts/mapgen/Dockerfile` downloads supercronic (`SUPERCRONIC_VERSION`, v0.2.49) and verifies it against the checksum pinned for the architecture. A build without network access cannot fetch it, and the alternative - vendoring the 14 MB binary into the repository - trades that for a large binary in git. Closing it would need an internal mirror or the binary in the repository.
- **The pinned checksums have to be updated with the scheduler**: the version and the two sha256 values (amd64 `a53ae236...`, arm64 `02aa0cb2...`) sit in one `case` block in the same Dockerfile, so an upgrade is a deliberate edit. Nothing checks that the pin matches upstream beyond the build failing if it does not; the arm64 asset is pinned but has never been built or run, because only `linux/amd64` images are published (see the entry above).

Conditions of `mapgen-failure-recovery`.

- **A failing import is visible only in the log and the exit status**: the script now retries and recovers by itself, but in the scheduled mode nobody is told that it keeps failing - supercronic writes the pass output into the container log and moves on. An unattended deployment can fail for weeks without notice. A notification after a failed pass (a webhook, or metrics the operator can alert on) would close it; the pass staying due means the retry itself needs no attention.

Pre-existing issues found during implementation of `msys-ci-font-environment`, not initiated by that change. Process in separate changes.

- **The Cairo backend treats a font file path as a font family name**: `MapPainterCairo::GetFont` hands `parameter.GetFontName()` straight to `pango_font_description_set_family` (`libosmscout-map-cairo/src/osmscoutmapcairo/MapPainterCairo.cpp`), so a caller that passes a font *file* gets a family lookup for a string that looks like a path. `Tests/src/PerformanceTest.cpp` receives `--font <path>` and passes it on unchanged (`MapParameter::SetFontName`), and `Tests/src/MapPainterShieldTest.cpp` names the family `Liberation Sans`; on a host that provides neither, both paint with the fontconfig fallback and only log `couldn't load font "..." falling back to "Sans ..., expect ugly output`. - **Nothing checks that both build systems register the same tests**: a test target has to be declared twice, once in `Tests/CMakeLists.txt` and once in `Tests/meson.build`, and the test name follows a different convention in each (the CMake macro names the test after the target, Meson takes a prose string). A test declared in only one of them is built and run by one build system and silently absent from the other: the `naviveylin-local` branch (PR #1773) registered its new `StringMatcherTest` in CMake only, which is how the gap surfaced. A check comparing the two rosters, or a single list both build systems read, would close it.
