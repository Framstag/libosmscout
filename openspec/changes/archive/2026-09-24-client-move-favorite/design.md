# Design

## Context

See `proposal.md` - Why. The relevant current state:

- `libosmscout-client/include/osmscoutclient/FavoriteLocationService.h` and its implementation
  already hold the favs of a group in a `std::vector<FavLocation>` inside a name-keyed
  `std::map<std::string, FavLocationGroup>`, mutated under a `std::shared_mutex` (write operations
  take `std::unique_lock lock(mutex_)`, readers `std::shared_lock`). The existing CRUD mutators
  therefore already define the locking and lookup pattern a move has to follow.
- The order of that vector is already the stored order: `Save()` writes the favs in vector order and
  `Load()` reads them back in file order, which the `fav-location-service` capability already covers
  for add/delete/rename.
- The Java surface is generated by hand: a declaration in
  `libosmscout-client-java/java/com/framstag/libosmscout/client/OSMScoutClient.java` and a matching
  `extern "C" JNIEXPORT` function in `libosmscout-client-java/src/OSMScoutClient.cpp`, which reaches
  the service through the `ClientData` handle owned by the client object.
- Groups are stored in a `std::map`, so group order is name order, not insertion order. This design
  does not touch that.

## Goals / Non-Goals

**Goals:**

- One positional move operation, reachable from C++ and from Java, that cannot lose the moved fav's
  data, cannot corrupt the group's other favs, and needs no caller-side knowledge of the list size.
- Keep the change additive and small enough to review on its own: source, JNI, Java declaration,
  tests.
- Keep the persisted representation unchanged, so no format negotiation and no migration.

**Non-Goals:**

- Reordering groups, or ordered groups in general (groups stay a name-keyed map).
- A bulk or multi-fav reorder operation, and any "move up by one" convenience API (callers can
  compute an index).
- Drag-and-drop UI work in this repository.
- Making `ClientData` own the service differently - that is the separate favorite-store ownership
  change, which will have to delegate this operation. This change is written so that delegating it
  stays a one-line forward.

## Decisions

**D1 - The target position refers to the list after the moved fav has been taken out.**
The caller names "where the fav ends up in the list of the group's other favs" (position `0` = first
place, position `size` = last place).
Alternatives:
- *Index into the list before removal*: the same numeric target means "before" or "after" the
  fav's own slot depending on the direction of the move, so every caller needs a direction-dependent
  off-by-one correction. A drop target from a UI yields the post-removal index directly.
- *Move relative to a named neighbour* (`moveBefore(group, fav, neighbour)`): needs a second name
  lookup with its own failure mode ("neighbour not found") and cannot express "move to the end"
  without a sentinel; drag-and-drop produces an index, not a neighbour.
- *Move by delta* (`move(group, fav, +1/-1)`): convenient for up/down buttons, but reaching a distant
  position takes many calls, each of them a separate store change, and it cannot express clamping
  meaningfully.
Chosen because it is the only form that a caller can derive from the data it already displays, and it
makes both ends of the list addressable by a constant (`0` and anything `>= size`).

**D2 - An out-of-range position is clamped, not rejected.**
Alternatives:
- *Return false on out-of-range*: forces the caller to read the group size first; the size can change
  between the read and the move, so the caller cannot make the call reliably, and "move to top" would
  need a size of `0` that may already be stale.
- *Throw or assert*: the repository avoids asserts that user input can trigger, and an exception
  would be a new error style in this API, which reports failures as `false`.
Chosen because clamping makes the two natural intents ("first", "last") expressible without a query
round trip, which is what a UI does when the user drops at the top or the bottom edge.

**D3 - The vector order stays the only representation of the order.**
Alternatives:
- *Store an explicit position/index attribute per fav*: duplicates state that can disagree with the
  array order, needs a tie-break rule for equal or missing values, and changes the file format and
  the type-config version policy for no gain.
- *Store a separate order list next to the fav list*: same duplication problem plus a new
  consistency rule for favs that are added or deleted; a fav missing from the order list would need a
  defined fallback position.
Chosen because the array order is already round-tripped by `Load()`/`Save()`, so the operation needs
no persistence work at all, and there is exactly one place where the order can be wrong.

**D4 - One service method with an unsigned position, plus one Java method whose negative value means
the first position.**
The service takes `size_t newIndex` (a negative position is not a concept in the C++ API); the JNI
entry point takes a Java `int` and maps a negative value to `0`.
Alternatives:
- *Two Java methods* (`moveFavoriteToTop`, `moveFavoriteToEnd`): more API surface, and neither can
  express an arbitrary target, so a middle position would still need the general method.
- *Reorder in Java and call `saveFavoriteLocations`*: that path rebuilds the whole store from Java
  objects, which is exactly what loses the attributes the Java model cannot express - the situation
  this change removes; it also replaces every group, not one fav, so unrelated content is written
  back for a single reorder.
- *Expose a signed position in C++ as well*: pushes a JNI-level convention into the library API and
  makes the meaning of the parameter depend on the caller's language.
Chosen because it keeps the C++ contract clean and puts the only Java-specific convention (negative
means first, which is how `List.add`-style callers think) in the one place that speaks Java.

**D5 - The move takes the service's existing write lock.**
Alternatives:
- *Lock in the JNI layer*: adds a second mutex with an ordering relation to the service's own, while
  leaving the C++ API racy for C++ callers.
- *No lock / lock-free swap*: the vector is mutated in place, so an unlocked move can be observed
  half applied (fav temporarily absent, or present twice) by `GetFavorites`.
Chosen because a per-call write lock is already the invariant of every other mutator, so the move
inherits the guarantee instead of adding a new one, and the spec can state "never observed half
applied" without qualification.

## Sequence diagram

```
Java caller                JNI bridge (OSMScoutClient.cpp)      FavoriteLocationService
    |                               |                                      |
    | moveFavorite(g, f, idx) ----->|                                      |
    |                               | getClientData(self): null check      |
    |                               | idx < 0 ? 0 : static_cast<size_t>    |
    |                               | MoveFavorite(g, f, idx) ------------>| unique_lock(mutex_)
    |                               |                                      | groupIt = groups_.find(g)
    |                               |                                      | favIt = scan favs for f
    |                               |                                      | erase(favIt)
    |                               |                                      | clamp idx to favs.size()
    |                               |                                      | insert(clamped, fav)
    |                               |<---------- true / false -------------|
    |<------ JNI_TRUE/JNI_FALSE ----|                                      |
```

Failure paths return before any mutation: unknown group and unknown fav both leave `groups_`
untouched, so the "no change on failure" scenario holds without a rollback.

## Risks / Trade-offs

- *Clamping hides a caller's stale index* (a caller that computed an index against an older list is
  silently served the last position) → the contract is documented in the header, the Javadoc and the
  spec, and both boundaries are tested; reporting the applied index instead would be a wider API
  change and is left out deliberately.
- *Index-after-removal differs from the "insert before index" intuition of `List.add(index, ...)`* →
  stated explicitly in the header, the Javadoc and a dedicated spec scenario, so a reader cannot
  miss it; the alternative (D1) makes every caller do the correction itself.
- *A no-op move reports success*, which can mask a wrong index → accepted: the contract is "true if
  the fav is at the target position afterwards", which is what a caller wants to know; making it
  false would break the two natural intents of D2.
- *Order is only stored as array order*, so an external tool that rewrites the JSON in another order
  changes the user's order → accepted: D3's alternatives replace a silent reordering with a silent
  disagreement between two sources of truth, which is worse for the same failure.
- *The JNI method is additive*, so a Java caller built against the new classes and run against an
  older native library fails to link the method → only callers that reorder favs are affected, and no
  existing method changes signature or meaning.
- *A C++ caller can still mutate the store through the existing service handle without a move*, so
  the operation is not the only writer → unchanged by this design; the separate favorite-store
  ownership change addresses who owns the handle.

## Migration Plan

No data migration: the file format, the JSON keys and the type-config/file-format versions are
untouched, and an existing favorite file is read as before. Deployment is a plain library update;
the new method appears in the same release as the Java declaration, and nothing in the repository
calls it yet, so no caller needs to be adapted. Rollback is a revert of the commit: files written by
a caller that used the new method are ordinary favorite files that an older library reads without
loss (the order is preserved, the method simply does not exist).

## Open Questions

- Whether a "move to top" convenience wrapper is worth adding on the Java side: deferrable, it would
  not change the specs or the approach.
