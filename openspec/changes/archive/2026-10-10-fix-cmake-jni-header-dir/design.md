# Design

## Context

See proposal.md — Why. The JNI headers of `libosmscout-client-java` are produced by one
`add_custom_command` in `libosmscout-client-java/CMakeLists.txt` (`:55-66`). Its OUTPUTs are the header of
`OSMScoutClient` and a javac stamp (`:48`, `:52`); `java_compile` depends on the header, and
`osmscout_client_java` depends on `java_compile` and includes the header directory (`:109`). The command
already removes the class directory before compiling; the header directory is only created.

## Goals / Non-Goals

**Goals:**
- The header directory of a build tree holds the headers of the Java sources present in that run.
- The C++ client keeps compiling against the same directory, unchanged otherwise.

**Non-Goals:**
- Cleaning anything else in the build tree, or changing the jar rule.
- Closing the same gap in the Meson build: the `javac` invocation of
  `libosmscout-client-java/java/meson.build` does not empty its header directory either, and the Meson build
  does not read `CMakeLists.txt`; that divergence is outside this change.
- Adding a permanent test registration; the verification is a named, retained run (below).

## Decisions

**D1 — Empty the header directory in the existing `javac` custom command, next to the class directory.**

Chosen: add `COMMAND ${CMAKE_COMMAND} -E rm -rf ${JNI_HEADERS_DIR}` before the existing
`make_directory ${JNI_HEADERS_DIR}` (`:61`), with the comment style the class directory already uses
(`:57-58`).

Alternatives eliminated by the evidence:

- *Let a header that is no longer declared simply be ignored.* `OSMScoutClient.h` is a declared OUTPUT, so
  CMake treats the directory as a cache keyed by the file it declares; nothing removes a sibling file, and
  the sentinel run on HEAD showed the extra header surviving a full rule execution. The C++ compiler also
  resolves includes against the directory, so a stale header is includable, not merely present.
- *Put the removal in `java_jar` or in the library target.* Both consume the header directory rather than
  produce it; `java_compile` is the only rule that owns its contents and the only one that must run before
  the C++ compile (`:132`).
- *Delete only the headers of sources that disappeared, computed from the source list.* The rule would
  need a second manifest to diff against, duplicating the failure mode `fix-java-jar-consistency` avoided
  when it chose to empty the class directory instead of tracking removals. Emptying is one line and cannot
  drift.

## Risks / Trade-offs

- [Deleting the directory forces `javac` to rewrite every header, so a header an unrelated consumer had
  modified in place is lost] → the directory is a build artifact, regenerated by the same rule; the C++
  build reads it after the rule ran.
- [A concurrent build reading the directory while it is removed] → the rule owns the directory and runs
  before `osmscout_client_java` compiles, the same serialization the class directory already relies on.
- [The `rm -rf` is broader than the stale header] → it removes only files under
  `${CMAKE_CURRENT_BINARY_DIR}/java/headers`, all of which this rule generates.

## Migration Plan

One-line build rule change; rollback is deleting the added command. No installed artifact, file format or
API is affected.

## Open Questions
