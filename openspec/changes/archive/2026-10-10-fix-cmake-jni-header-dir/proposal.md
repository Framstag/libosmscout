# Proposal

## Why

Root cause: The `java_compile` custom command in `libosmscout-client-java/CMakeLists.txt` prepares the
JNI header directory with `make_directory` alone (`:61`) and then runs `javac -h ${JNI_HEADERS_DIR}`
(`:62`), which emits one header per class that declares a native method and only adds or overwrites
those it compiles — so the header of a removed or renamed class stays behind in the very directory
`osmscout_client_java` includes (`:109`).
Evidence:    On HEAD, `openspec/changes/fix-cmake-jni-header-dir/evidence/red-case-java_compile-target.log`
— after writing the sentinel `com_framstag_libosmscout_client_OSMScoutClient_removedMethod.h` (a JNI
name no current source declares) and forcing the rule with
`rm -f build/libosmscout-client-java/java/headers/com_framstag_libosmscout_client_OSMScoutClient.h`,
`cmake --build build --target java_compile` ran `[1/1] Compiling Java sources and generating JNI
headers` (rc=0) and the sentinel was still listed: `RED: stale sentinel header survived the
header-generating target`, 2026-10-10T14:44:58+02:00.
Repro:       the log above; the defect is latent today — the directory held exactly the four headers of
the current sources and no stale one (`evidence/headers-current.txt`), so the run constructs the stale
header instead of relying on an existing file.
Spec:        `client-java-cmake-build` / JNI header generation
(`openspec/specs/client-java-cmake-build/spec.md:19`)   Guideline: none — this is a build rule, no C++ or
Java source convention changes.

The class directory already got this treatment: `fix-java-jar-consistency` (`8c421a215`,
`client-java: rebuild the jar when the Java sources change`) added, with the comment "javac only adds
class files, so a class whose source was removed would stay in the jar forever; start from an empty
directory so the jar mirrors the sources.", the line
`COMMAND ${CMAKE_COMMAND} -E rm -rf ${JAVA_CLASSES_DIR}`. The header directory, generated by the same
`javac` run, was left out.

## What Changes

- The CMake JNI header generation starts from an empty `${JNI_HEADERS_DIR}`, so the directory mirrors the
  current Java classes: after a class is removed or renamed, its header is gone from the next build.
- The headers of the current sources are still generated, and the C++ client library still compiles
  against that directory.
- No Java API, native interface, installation directory or Meson build behavior changes.

## Capabilities

### Modified Capabilities

- `client-java-cmake-build`: the JNI header generation requirement gains the contract that the header
  directory contains the headers of the current sources, with no header of a removed source left behind.

## Impact

- `libosmscout-client-java/CMakeLists.txt` — one `rm -rf` command added to the `java_compile` custom
  command.
- No change to the Java sources, the C++ JNI implementation, the shared-library target, the jar rule, the
  install rules, or the Meson build.
