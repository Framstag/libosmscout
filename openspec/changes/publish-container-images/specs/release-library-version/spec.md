# Spec Delta

## Purpose

Gives every release its own library version, separate from the release's chronological version, so
that the version build artifacts and generated database metadata report identifies the release that
produced them instead of being frozen across releases.

## ADDED Requirements

### Requirement: Every release establishes its own library version

Each release SHALL establish a library version that is separate from the release's chronological
version and that follows its own scheme. Two consecutive releases SHALL NOT report the same library
version. The source revision of a release SHALL carry that release's library version, so that
building the released source reproduces artifacts reporting it.

#### Scenario: The library version identifies the release

- **GIVEN** two consecutive releases
- **WHEN** the library version of each is determined
- **THEN** the two library versions SHALL differ

#### Scenario: The library version is not the chronological version

- **GIVEN** a release whose chronological version is X
- **WHEN** the library version of that release is determined
- **THEN** the library version SHALL follow its own scheme and SHALL NOT be derived from X

#### Scenario: Building the released source reproduces the reported version

- **GIVEN** a release whose library version is Y
- **WHEN** that release's source revision is built by anyone from the published sources
- **THEN** the resulting build artifacts SHALL report Y

### Requirement: Release artifacts report the release's library version

The artifacts of a release SHALL report that release's library version, including the import tool
identity recorded in generated database metadata, and the library version tag published for the
release SHALL match it.

#### Scenario: Generated database metadata carries the release's version

- **GIVEN** a database generated by the import tool of a release whose library version is Y
- **WHEN** the database metadata is read
- **THEN** the recorded import tool version SHALL be Y

#### Scenario: Drift between two releases is detectable

- **GIVEN** databases generated by two consecutive releases
- **WHEN** their recorded import tool versions are compared
- **THEN** the versions SHALL differ and SHALL allow the generating release to be identified

#### Scenario: The published image tag matches the recorded version

- **GIVEN** a database whose recorded import tool version is Y, generated by a released import tool
- **WHEN** a consumer looks for the container image of the tool that generated it
- **THEN** a published image tag equal to Y SHALL exist for the regeneration image of that release

### Requirement: Library version compatibility

The major component of the library version SHALL change only for a deliberate compatibility break, so
that the shared libraries of consecutive releases remain interchangeable for consumers that link
against the existing major version.

#### Scenario: Consecutive releases keep the same major component

- **GIVEN** two consecutive releases that do not contain a deliberate compatibility break
- **WHEN** the major component of their library versions is compared
- **THEN** the two major components SHALL be equal

#### Scenario: A compatibility break is a deliberate act

- **GIVEN** a release whose library version has a different major component than the previous release
- **WHEN** the release is prepared
- **THEN** that change SHALL be the result of an explicit decision recorded for that release and not
  a side effect of the release's chronological version
